# 模块化与性能改造第一阶段（2026-10-15）

本版本不启动旧任务、不改历史 raw/config/queue、不迁移账号、不恢复定时心跳。旧 CLI、导入路径、字段和结束判据保持兼容；没有真实 X 速度结论。

## 代码地图

```text
tools/
  x_keyword_collector.py           兼容入口、搜索协调、既有作者/报表功能
  x_continue_saved_cursors.py      原独立续采入口、账号/计划/保护控制
  x_read_checkpoint.py             只读查看权威续采检查点
  x_workbench/
    query.py                      时间戳查询、日期切片/校验
    request_identity.py           请求 query/cursor 关联与 URL 构造
    parsing.py                    JSON → 帖子、用户字段、下一 cursor
    policy.py                     唯一结束分类、覆盖接受与修复队列规则
    browser.py                    Chrome 响应缓存、滚动触发、精确 cursor 请求
    http_transport.py             隔离 HTTP 实验传输接口，不是默认生产后端
    storage.py                    JSON 原子替换、可选 SQLite 增量事务
    state.py                      界面/审计/统计/导出的统一权威快照读取
    continuation_view.py          独立续采视图、快照版本及真实进程观察
    resume.py                     只允许核实过的人工暂停恢复，不清其他保护
    evidence.py                   仅供实时状态使用的有界证据缓存
    metrics.py                    分阶段计时，不记录凭证/请求正文
```

原 `x_keyword_collector` 继续导出历史函数；旧维护工具无需同时修改全部 import。纯查询、解析、政策、存储、计时模块可在没有 Playwright 的 Python 中导入。浏览器控制依赖仅位于浏览器模块/旧协调入口。作者补查、报表、UI 等旧代码尚未全部拆完，本版不假称整仓库已完成重写。

## 两条路线都用 cursor

- 生产默认：X 网页生成签名请求，程序优先取已缓存的匹配响应，否则滚动触发；断点和部分尾部核验可重载网页生成指定 cursor 请求。
- HTTP 实验：调用方提供隔离的 HTTP 客户端、有效会话和逐次新签名，直接请求保存的 cursor。
- 公用：`collect_search_http` 与浏览器入口调用同一个分页协调器，继续用相同的解析、日期筛选、去重、页级检查点、限流等待与结束政策。HTTP 入口只支持 Latest，查询须精确一致，至少两秒间隔。

HTTP 层没有直接接入 twscrape，没有复制上游源码、读取原 A–E Chrome profile、自动登录、轮换账号、忽略 404 或隐藏空响应。它默认禁止请求，必须由隔离实验调用方显式打开并注入新签名提供者；目前没有把签名生成/会话初始化接到正式 UI/CLI。响应中的 401/403/404/429 仍交给共同保护处理，不自动重试。严格限制 HTTPS SearchTimeline 端点，不跟随重定向。

**完成的是接口与离线公共流程验证，不是完整真实账号可用性验收。** 不能把现有 Cookie/旧 transaction ID 复制进去便宣称可以去掉 Chrome。真实无浏览器路线仍需隔离账号验证签名、登录、退避、长链续采与结果对照。没有修改原任务默认路线。

## 保存优化及兼容边界

### 默认 JSON

旧入口默认仍写原 JSON；不能让旧报表在不知情时读到过期快照。原子写入现在使用独立临时文件、flush/fsync、Windows 共享占用有限重试和原子替换，写入失败不覆盖旧文件。更强耐久性有额外开销，不能宣称这个改动单独提升速度。并发任务仍须使用原账号锁，独立临时文件不等于允许两个同账号写者。

### 可选 SQLite（当前只接入独立 cursor 续采）

`x_continue_saved_cursors.py` 增加 `--checkpoint-backend sqlite`；默认仍为 `json`。这是存储选择，不改变关键词、账号、日期、排序、graphql/deferred/3/15000、coverage_first 或退避。没有对现有任务执行该选项。

启用后，输出目录中：

| 文件 | 含义 |
|---|---|
| `continuation_raw.sqlite3` 与可能存在的 `-wal` / `-shm` | **权威检查点**；帖子与最新状态/页码/cursor 同事务提交 |
| `continuation_raw.json` | 兼容完整快照；每 20 次保存事务及日期结算、退出时导出，运行中可能滞后 |
| `status.json` | 每次保存后更新，含后端、generation、权威路径及计时；不能仅用此文件证明采集完整 |
| `timings.json` | 本进程计时汇总，正常退出后包含导出计时 |

SQLite 使用 WAL 和 synchronous=FULL；首次导入独立续采自己的 JSON，之后每页只插入新增帖子，更新较小的运行元数据。新增帖子与 cursor 原子提交；数据库错误归为致命保存错误，不进入网络重试。已有帖子为追加只读约定，本后端不用于原作者补全/旧帖修改。所有帖子仍在工作进程内存中，本版不声称已解决累计内存占用。

恢复优先读 SQLite：即使最后兼容 JSON 较旧，也恢复事务里更晚的帖子与 cursor。JSON 的哈希锚点被改动、数据库缺行、计划不符、新 guard_hold 都阻止盲目恢复。已有 SQLite 时用默认 JSON 启动会明确拒绝，避免退回旧快照。持久化冷却尚未到期时，恢复实例在启动浏览器前继续等待，不能通过重启缩短 reset/退避。

当前界面、独立续采审计、快照脚本、通用TXT导出及读取助手已通过`x_workbench.state.read_state`读取权威状态；未迁移的历史实验/维护脚本仍不能直接用旧JSON统计SQLite模式实时数据，尤其不能照搬旧暂停/恢复脚本。实时查看也可用`x_read_checkpoint.py <continuation_raw.json>`。不要单独复制正在运行的数据库文件而丢掉WAL，备份应在安全停止后整体保存或使用SQLite backup。旧五批原始数据不自动转换，独立续采仅在本次明确授权恢复时显式选用SQLite。

本模式仍须在真实任务前做验收，故不默认打开。断电模拟只验证事务/恢复逻辑，不能替代硬盘与操作系统的真实断电测试。极端地在 JSON 替换和锚点更新之间崩溃，会安全拒绝并要求核验，不悄悄选择较旧数据。

## 第三阶段：统一读取与显式恢复

- `read_state`每次捕获一个已提交版本；JSON版本为内容SHA256，SQLite版本为事务generation。SQLite元数据与帖子在同一读取事务中取得，不混用另一个时刻的status计数。预览只读取最后若干条，计数仍是完整数据库计数；审计/导出/恢复完整核验快照锚点。实时界面可对未变化的兼容文件哈希作有界元数据缓存，但不以此替代最终验收。
- SQLite损坏、快照被手工改动或没有已提交状态时明确报错，**不得悄悄退回旧JSON，更不能显示为0条**。
- 界面新增“独立游标续采·最新存档”，显示本轮实际新增、当前日期/页码、已核验续采末端、待处理日期、实际进程、后端与快照版本。原始批次和独立新增不混称总量。旧工作台管理器的开始/暂停按钮不控制独立worker，面板明确标为只读；原任务启动器发现同账号独立worker时拒绝再启动。
- `/api/continuations`、`/api/continuation?node=a`、`/api/continuation/export?node=a`统一读取；TXT下载与receipt记录同一个捕获版本，运行中后一次请求可能读到新版本，这是正常进展，不是统计矛盾。
- 原历史界面的帖子数改为原始存档实际计数；跨原批次去重不再以旧research_dataset导出冒充最新数据。启动时先按账号配置筛选再解析大文件，减少跨账号重复读取。
- `x_guard_audit`增加独立续采子报告；`x_audit_continuations.py`只读核对五批存档和真实进程。原批次完成与独立续采末端验证严格分开，旧页链缺证不反向补证。
- `x_resume_verified_five.py --pause-dir ...`默认仅预检。只有明确`--launch`才备份并恢复；验证当前文件与安全暂停备份SHA一致、帖子ID唯一且全保留、计划/原配置/全部历史源无漂移、账号无worker或专属Chrome、锁与旧PID一致、没有新保护。只结算与暂停报告完全吻合的已知人工关闭driver标记，未知/登录/HTTP保护一律保留。恢复前再检查文件未变化；原账号、run_id、cursor、查询条件与退避不改。不恢复自动心跳。

新增验收：有意让JSON落后一页，界面、审计和TXT仍同为数据库最新条数与相同revision；修改兼容JSON保护后返回503而非旧计数；人工暂停恢复拒绝未知保护、变更文件、重复/缺失ID及未核实停止。真实长链运行与无浏览器签名测速仍不能由这些离线测试替代。

## 重复核验优化

仅实时状态计算启用进程内有界缓存：默认最多 4096 个证据、原始字节合计 32 MiB，键包含路径、期望 SHA256；每次检查文件身份、大小、mtime、ctime。改动、删除或新哈希会重新读盘核验；query/cursor/guard 等政策条件仍每次判断。缓存值不供外部修改。

默认公共政策函数、最终结束验收和恢复核验不处于缓存作用域，重新读取实际证据并检查 SHA256。缓存不是防恶意篡改的信任依据，不能用实时状态命中取代最终核验。没有把超时、重复 cursor、连续无新增重新命名为“到底”。

## 分阶段计时

`timings.json` 使用固定阶段名：请求/触发等待、解析、日期过滤与去重、证据写入、证据核验、检查点写入、状态生成、正常节奏等待、reset 等待、退避、导出和搜索总耗时。记录调用数、失败数、秒数与最大值，不记录 Cookie、签名、Authorization 或任意错误正文。

计时只描述本进程；重启不会把它伪装成历史累计耗时。阶段存在嵌套，**不能把所有秒数相加当总耗时**。单独搜索入口不包含浏览器初始化；普通采集入口的`run_total`包含函数内初始化和导出，仍不覆盖CLI启动前工作及所有历史UI/作者维护入口，不把此文件当完整端到端测速工具。

### 第二轮效率改造

- 普通采集和独立续采的检查点回调改为只处理累计列表中新追加的帖子；首次、重试换列表时仍完整去重，保存成功后才确认增量前沿。即使没有新帖子，新的页码/cursor仍照常持久化。累计列表属于分页器，必须只追加，不允许原地改写已确认的旧帖。
- 普通采集不再逐页复制整个累计列表；独立续采按日期索引自己的新增帖，避免每日期/重试反复扫描全部新增记录。原始源文件完整性检查、保护和退避不省略。
- 普通页级保存只构造一次修复队列和自填位置待补队列，复用于状态和队列文件；这不发起作者查询。搜索前仅阶段变化时保存检查点，不重建内容相同的CSV/HTML/ZIP；日期结算和收尾仍导出。
- 首个正式搜索响应不重复解析。断点恢复的首页仍只作健康/日期核验，不能拿它代替保存cursor的后续页。
- 已归档的续采响应直接被空尾页/无cursor结尾证据引用，避免同页写两份文件。可选写入摘要由实际序列化字节生成，不再为生成摘要立即重读刚写的文件；**最终政策核验仍读取磁盘文件并比对摘要**。
- 增加JSON序列化、检查点合并计时及`self_seconds`（扣除嵌套已计时阶段）。普通采集的`run_total`覆盖采集函数与其初始化/导出，不包含CLI启动前工作，也不是整台机器的性能采样。独立续采仍使用本进程已有各阶段汇总。

合成工作量验收：已有10,000条，再逐页增加20条、共20页，原回调累计扫描204,200条次，增量前沿扫描10,400条次；只减少这一环节的重复工作，不可换算成请求/整体采集倍速。追加式假设、重试重扫、空页游标、队列构造、字节摘要与末端证据去重复用，由`tests/test_x_efficiency_regressions.py`验证。

这些默认生效的CPU/I/O优化不等于默认切换SQLite：兼容性未验收的旧JSON报表仍需保留原行为，可选SQLite及无浏览器实网路线的边界不变。没有降低请求间隔、减少退避、并发占用账号或放宽结束判据。

## 已验证与仍待验证

- 已验证：旧结束分类/续采兼容；缓存失效及最终重哈希；原子写失败保留旧文件；SQLite 增量、事务回滚、恢复更晚 cursor、手工 JSON 保护不被绕过；持久化冷却在浏览器启动前等待。
- 已验证：完全合成的两路线公共分页，得到相同 ID 集合与三个规范空尾页的结束判据；测试没有真实 X 请求。
- 待验证：隔离 HTTP 签名/会话初始化、真实网络稳定性、真实速度和资源占用、真实长链异常恢复。不能宣称平台全量或 HTTP 更快。
- 不改：原账号与收集条件、HTTP 保护/退避、底部定义、历史记录及作者所在地补查策略。

测试入口：`python -m pytest tests/test_x_workbench_components.py`。同时运行现有 X collector/UI/guard/cursor/404 测试。部分既有 UI 测试在本机临时 HTML 上使用无头浏览器；不是登录 X、不是恢复研究采集。

离线存储基准可运行 `python tools/x_offline_checkpoint_benchmark.py`：只生成临时合成帖子，不读账号/历史数据。以已有 10,000 条、再追加 20 页每页 20 条为例，本机 3 轮的页提交耗时中位数为 JSON 约 0.561 秒、SQLite 约 0.049 秒（SQLite 含第 20 页的完整快照）；SQLite 另需首次导入约 0.077 秒、结束快照约 0.041 秒。这只是约 3.2 MB 的合成存储实验，不含网络、解析、证据/状态生成，不能换算成采集倍速；完整输出由脚本提供。
